# 결정 기록 (Decision Log)

수치, 임계값, 기법을 정하거나 바꿀 때마다 여기에 기록한다. 항목마다 **근거 유형**을 표시한다.

| 근거 유형 | 뜻 |
|---|---|
| 측정 | 이 저장소나 운영 환경에서 직접 측정한 값 (재현 방법 포함) |
| 공식 제약 | AWS·라이브러리 문서에 정해진 한도나 호환 범위 |
| 문헌 | 논문이나 널리 인용되는 자료 |
| 관행 | 업계에서 일반적으로 쓰는 방식 |
| 판단 | 근거 없이 정한 값. **재검토 조건을 반드시 적는다** |

## 평가 하네스 (`eval/`)

### E-01 정답 등급은 규칙으로 판정한다 (LLM 판정 미사용) · 2026-11-05 · 판단

- **근거**: 코퍼스와 질의를 LLM으로 만들었다. 판정까지 LLM에 맡기면 LLM 기반 검색에 유리하게 치우칠 수 있다(순환 편향).
- **대가**: 의미상 관련이 있어도 구조화 속성으로 표현되지 않은 문서는 0점이 된다.
- **재검토**: v2에서 독립적으로 작성한 질의와 사람 판정(pooling)을 도입할 때.

### E-02 '정답' 기준은 등급 2 이상 · 2026-11-05 · 판단

- **근거**: 등급 1은 "카테고리만 맞고 핵심 조건 일부가 다름"이라 구매자 입장에서는 정답이 아니다. 대신 nDCG에는 등급(0~3)을 그대로 넣어 부분 관련성을 반영한다.

### E-03 주 지표는 nDCG@10 · 2026-11-05 · 측정 + 코드

- **측정**: 질의별 정답 수 R은 최소 1, 중앙값 4, 평균 4.9, 최대 22다. R이 10을 넘는 질의가 91개 중 6개다. 이런 질의에서는 Recall@10이 구조적으로 1에 닿을 수 없다. nDCG@10은 이상적인 순위로 정규화하므로 R 차이에 덜 민감하다.
- **@10의 근거**: `vector-search/index.ts`의 기본 `topK = 10`과 맞췄다.

### E-04 질의당 정답 수 상한 25 · 2026-11-05 · 판단

- **근거**: 너무 넓은 질의를 데이터셋 검증 단계에서 걸러내는 안전장치다. 현재 최대값은 22다.
- **실제로 걸린 사례**: q019 "잔존용량 80% 이상 배터리 팩"이 정답 29개로 걸려 85%로 좁혔다.
- **재검토**: 코퍼스 규모를 바꿀 때 비율로 다시 정한다.

### E-05 코퍼스 300개, 질의 91개, v2 목표는 질의 약 350개 · 2026-11-05 · 판단 → 측정

- **v1**: 300개와 100개 안팎은 계획 단계의 판단값이다.
- **측정**: test 44개로 쌍체 비교한 nDCG@10 차이의 95% 신뢰구간 반폭이 **±0.036**이다(`reports/2026-11-05-v1-experiments.json`). 따라서 약 0.035 이하의 개선은 이 데이터셋으로 구분할 수 없다.
- **v2 목표**: 신뢰구간 폭은 1/√n에 비례한다. 반폭을 ±0.018로 줄이려면 test 질의가 약 176개 필요하다. 그래서 dev와 test를 합쳐 약 350개를 목표로 한다.

### E-06 카테고리 분포 (배터리 70, 모터 45, 인버터 35, …) · 2026-11-05 · 판단

- **근거**: 프로젝트의 핵심 품목인 배터리·모터·인버터에 절반(150/300)을 배정했다. 실제 시장의 분포는 아니다.
- **주의**: IDF처럼 문서 빈도에 의존하는 결론(E-16)은 이 분포에 민감하다.

### E-07 생성 시드 20261105 · 2026-11-05 · 판단

- 값 자체에는 의미가 없다(작성 날짜). 재현성을 위해 고정한 값이다.

### E-08 회귀 게이트 허용치 0.01 · 2026-11-05 · 측정

- **측정**: BM25 오프라인 실행은 결정적이다. 같은 커밋에서 두 번 실행하면 지표가 같다.
- **계산**: 질의 1개의 nDCG가 1에서 0으로 무너지면 전체 평균은 1/91 ≈ 0.011 떨어진다. 허용치 0.01이면 전체 수준에서 질의 하나의 실패도 잡는다.
- **검증**: 회귀를 일부러 넣었을 때 게이트가 실패했다(exit 1).
- **재검토**: LLM 쿼리 확장처럼 결과가 비결정적인 구성을 게이트에 넣을 때. 그때는 k회 반복 실행의 분산으로 허용치를 다시 정한다.

### E-09 CI 게이트는 BM25만 대상으로 한다 · 2026-11-05 · 공식 제약

- **근거**: vector와 hybrid 구성은 임베딩 캐시(3.76MB, 커밋하지 않음)와 AWS 자격 증명이 필요하다.
- **재검토**: 캐시를 CI 아티팩트나 S3로 제공하면 prod-hybrid도 게이트에 추가한다.

### E-10 임베딩 캐시는 커밋하지 않고 재생성한다 · 2026-11-05 · 측정

- **결정성**: 샘플 5개(질의 3, 문서 2)를 다시 임베딩했더니 코사인 유사도 1.00000000, 최대 오차 5.0e-7이었다. 이 오차는 캐시를 소수점 6자리로 반올림할 때 생기는 오차의 상한과 같다.
- **비용** (2026-11-05 실측)
  - 입력 391개, 63,391 토큰 (CloudWatch `AWS/Bedrock InputTokenCount`)
  - 단가: AWS Price List `APN2-TitanEmbeddingV2-Text-input-tokens` = $0.000024592 / 1K 토큰
  - 합계 **약 $0.0016**, 소요 16초

### E-11 지표는 직접 구현한다 (ranx 미사용) · 2026-11-05 · 판단

- **근거**: 지표가 nDCG·Recall·MRR·P@k 네 개뿐이다. 이것 때문에 numba 의존성을 추가할 이유가 없다.
- **정확성**: `tests/test_metrics.py`에서 손으로 계산한 값과 비교해 검증한다.

### E-12 시스템 비교는 질의별 쌍체 부트스트랩 CI와 무작위화 검정 · 2026-11-05 · 문헌 + 관행

- **근거**: IR 평가에서는 질의 단위 쌍체 검정이 표준 관행이다. Smucker, Allan, Carterette (CIKM 2007)은 무작위화 검정을 권장했다.
- **반복 횟수**: 10,000회. p = 0.05 근처에서 몬테카를로 표준오차가 약 0.002다.
- **p 표기**: 무작위화 검정의 p는 최소 1/(n+1)이라 "<0.001"로 표기한다.

### E-13 구성은 dev에서 고르고 test에서 확인한다 · 2026-11-05 · 관행

- **근거**: 구성 46개를 같은 질의로 비교한 뒤 최고값을 고르면 그 점수는 과대평가된다(선택 편향).
- **분할 방법**: qtype별로 층화하고, qid의 sha256 순서로 dev와 test를 번갈아 배정한다. 결과는 dev 47개, test 44개다.

### E-14 실험용 BM25는 빠른 구현을 쓰되, 프로덕션 함수와 대조한다 · 2026-11-05 · 측정

- **근거**: 프로덕션 `bm25Score`는 호출할 때마다 문서 빈도를 다시 계산한다. bigram 토크나이저로 46개 구성을 돌리기에는 너무 느리다.
- **검증**: 실행할 때마다 다음 두 가지를 확인하고, 다르면 중단한다.
  - 공백 토크나이저: 프로덕션 `calculateBM25Scores`와 점수 차이 ≤ 1e-9 (질의 4개 × 문서 300개)
  - 후보 20개 구성: 프로덕션 `hybridSearch`와 점수 일치

### E-15 독립 검색 결합에서 min-max의 최대값과 최소값이 같으면 0 · 2026-11-05 · 판단

- **근거**: 정보가 없는 신호는 결합에 기여하지 않게 했다.
- **참고**: 프로덕션 `normalizeBM25Scores`는 이 경우 1을 반환한다. prod 구조 구성은 프로덕션 함수를 그대로 쓴다.

### E-16 결합 기법 후보: 볼록 결합(convex)과 RRF k ∈ {10, 30, 60, 100} · 2026-11-05 · 문헌

- **RRF**: k = 60은 Cormack, Clarke, Büttcher (SIGIR 2009)가 제안한 값이다. 주변 값으로 민감도를 확인한다.
- **볼록 결합**: Bruch, Gai, Ingber (ACM TOIS 2023)는 튜닝한 볼록 결합이 RRF보다 낫다고 보고했다. v1 결과도 같은 방향이다(dev 기준 볼록 결합 0.863, RRF k=30 0.835).

### E-17 v1 실험 결론: 프로덕션 변경은 보류하고 v2로 확인한다 · 2026-11-05 · 측정

- **결과** (test 44개, 현재 프로덕션 `prod-ws-a0.7-c20` 대비 nDCG@10)

|---|---:|---|---:|

### E-18 후보 모델 실측 방법 · 2026-11-05 · 측정

- **경로**: 프로덕션과 같은 코드를 쓴다(`search-llm.ts` 프롬프트·파싱, `invokeClaude`, Titan 평균 임베딩, vector-search와 같은 prod-hybrid). 실행기는 `eval/ts/llm-candidates.ts`, 리포트 생성은 `eecar_eval.llm_candidates`다.
- **호출 간격을 분당 40회로 제한한다**
  - 계정 쿼터가 global cross-region 분당 요청 50이다(Haiku 4.5, Sonnet 4.6 모두, Service Quotas 조회).
  - 제한 없이 동시 4개로 첫 실행을 했을 때 SDK 재시도 3회 후에도 쿼리 확장 21/91, 결과 설명 14/20이 `ThrottlingException`으로 실패했다. 이 상태로는 파싱 성공률과 지연을 잴 수 없다.
- **결과 설명 비교 조건**: 모든 모델에 같은 입력(확장 없는 prod-hybrid 상위 10, 정렬한 qid 앞 20개 질의)을 준다.
- **쿼리 확장 비교 조건**: 확장 결과는 비결정적이므로 Haiku 4.5는 2회 실행해 실행 간 차이를 함께 보고한다. 기준은 확장 없는 prod-hybrid다. 레거시 모델이 차단된 뒤 프로덕션이 실제로 내는 결과가 이것이다.

### A-12 Claude 4.7 이후 모델 접근 불가: 원인은 계정 쿼터 0 (처음에는 약정으로 오판) · 2026-11-05 · 측정

> **정정**: 처음에는 이용 약정 미수락을 원인으로 판단했다. 그러나 약정을 수락한 뒤에도 호출이 막혔다. 아래 "쿼터 조사"가 최종 결론이다.

- **증상**: `global.anthropic.claude-haiku-5-5`·`claude-sonnet-5-5` 호출이 `AccessDeniedException: ... is not available for this account`로 실패한다. 4.7 이후 모델과 5.x 모두 같다. Haiku 4.5, Sonnet 4.6, Opus 4.5·4.6은 동작한다.
- **원인** (`bedrock:GetFoundationModelAvailability`, boto3 1.43)

| 모델 | 약정(agreement) | 권한 | 자격 | 리전 |
|---|---|---|---|---|
| Haiku 4.5, Sonnet 4.6 | AVAILABLE | AUTHORIZED | AVAILABLE | AVAILABLE |
| Haiku 5.5, Sonnet 5.5 | **NOT_AVAILABLE** | AUTHORIZED | AVAILABLE | AVAILABLE |

  권한, 자격, 리전 가용성은 모두 갖춰져 있고 **이용 약정만 수락하지 않은 상태**다.
- **해결 방법**: Marketplace offer 약정을 수락한다. 콘솔의 Bedrock 모델 접근 화면이나 `CreateFoundationModelAgreement(modelId, offerToken)`으로 할 수 있다. 현재 IAM 사용자에게 필요한 권한이 있다(`iam simulate-principal-policy` 결과 allowed).
- **약정 조건** (offer 요금표, 1M 토큰당 USD, Global Standard)

| 모델 | 입력 | 출력 |
|---|---:|---:|
| Haiku 5.5 | 0.1 | 0.5 |
| Haiku 4.5 (비교) | 1 | 5 |
| Sonnet 5.5 | 2 | 10 |

  사용량 기반 요금이고 선불 비용은 없다. "No refunds" 조건이 붙어 있다. Haiku 5.5는 Haiku 4.5보다 입출력 단가가 **10배 낮다**.
- **약정 수락 후 (사용자 승인, 2026-11-05)**
  - `CreateFoundationModelAgreement`로 두 모델의 약정을 수락했다. 약 60초 뒤 상태가 AVAILABLE이 됐다.
  - 그 뒤 5분 동안 재시도해도 InvokeModel·Converse 호출은 계속 `not available for this account`였다. **약정은 원인이 아니었다.**
- **실제 원인: 계정 단위 접근 제한**
  - Anthropic 공식 문서("Claude in Amazon Bedrock (Opus 4.7 and later)")에 따르면 4.7 이후 모델은 새 Messages 엔드포인트 `bedrock-mantle`로 제공된다. 접근 기준은 Amazon이 모델별로 정한다. 문서상 Sonnet 5, Opus 4.8, Haiku 4.5는 "모든 고객에게 열림"이고, Haiku 5.5와 Sonnet 5.5는 "See Access"다.
  - 새 엔드포인트를 직접 호출했다(`AnthropicBedrockMantle`, IAM `bedrock-mantle:CreateInference` 허용 확인).

| 리전 | 결과 |
|---|---|
| ap-northeast-2 | Haiku 5.5·Sonnet 5.5·Haiku 4.5: 404 "does not exist" / Sonnet 5: 403 "not available for this account" |
| us-east-1 | Sonnet 5·Haiku 4.5·Opus 4.8 (모두 "열림" 모델): 403 "not available for this account" / Haiku 5.5·Sonnet 5.5: 404 |

  - 결론: 문서상 모든 고객에게 열린 모델까지 막혀 있으므로 **이 계정이 새 엔드포인트를 쓸 수 없는 상태**다. 셀프서비스로 해결할 방법은 찾지 못했다. 커뮤니티(re:Post)에도 같은 증상과 "사용량에 따라 점진적으로 확대된다"는 언급이 있지만, 원문을 열지 못해 2차 출처로만 남긴다.
  - 조치: AWS Support 케이스(Account and billing)로 계정 활성화를 요청한다. 사용자가 진행한다.
  - 영향: 약정은 사용량 기반이라 호출이 없으면 비용이 없다.
- **결정**: 교체 후보는 지금 호출 가능한 ACTIVE 모델인 **Haiku 4.5**(InvokeModel·global profile)와 비교용 **Sonnet 4.6**으로 정한다. 계정이 활성화되면 Haiku 5.5를 같은 평가 절차로 다시 비교한다. Haiku 5.5의 단가는 Haiku 4.5의 1/10이다.
- **쿼터 조사로 확인한 최종 원인** (2026-11-05, Service Quotas `list_service_quotas` / `list_aws_default_service_quotas`, ap-northeast-2·us-east-1 결과 동일)

| 모델 (global cross-region 분당 토큰) | 계정 적용값 | AWS 기본값 | 호출 |
|---|---:|---:|---|
| Haiku 4.5 | 5,000,000 | 5,000,000 | 됨 |
| Sonnet 4.6 | 6,000,000 | 6,000,000 | 됨 |
| Haiku 5.5 | **0** | 10,000,000 | 막힘 |
| Sonnet 5.5 | **0** | 6,000,000 | 막힘 |
| Sonnet 5, Opus 4.7·4.8·5.5 | **0** | 6M~30M | 막힘 |

  - 동작하는 모델도 분당 요청 수는 기본 10,000이 아니라 **50**으로 낮게 잡혀 있다(A-13).
  - 쿼터 증설 요청에 기본값 이하의 값을 넣으면 "기본값보다 큰 값을 넣어야 한다"며 거부된다. 즉 0은 기본값보다 낮게 조정된 상태가 아니라 **계정에 대한 의도적인 제한**으로 보인다. 사용 이력이 적은 계정에 대한 AWS의 제한으로 추정하지만, 공식 근거는 없다.

  - 그 사이 적용값은 0으로 그대로였고 호출도 계속 거부됐다. 승인되면 A-14 하네스로 Haiku 5.5를 다시 비교한다.

### A-15 지표는 EMF를 stdout에 직접 쓴다 (Powertools 미도입) · 2026-11-05 · 공식 제약 + 판단

- **공식 제약**

- **판단**: 지표가 몇 개뿐이라 Powertools를 Layer에 넣는 대신 20줄짜리 유틸로 시작한다. 2주차에 Powertools(Logger·Idempotency)를 도입할 때 Metrics로 옮길지 다시 판단한다.
