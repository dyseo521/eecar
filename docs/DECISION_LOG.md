# 결정 기록 (Decision Log)

수치, 임계값, 기법을 정하거나 바꿀 때마다 여기에 기록한다. 항목마다 **근거 유형**을 표시한다.

| 근거 유형 | 뜻 |
|---|---|
| 측정 | 이 저장소나 운영 환경에서 직접 측정한 값 (재현 방법 포함) |
| 공식 제약 | AWS·라이브러리 문서에 정해진 한도나 호환 범위 |
| 문헌 | 논문이나 널리 인용되는 자료 |
| 관행 | 업계에서 일반적으로 쓰는 방식 |
| 판단 | 근거 없이 정한 값. **재검토 조건을 반드시 적는다** |

## 평가 하네스 (`eval/`)

### E-01 정답 등급은 규칙으로 판정한다 (LLM 판정 미사용) · 2026-11-05 · 판단

- **근거**: 코퍼스와 질의를 LLM으로 만들었다. 판정까지 LLM에 맡기면 LLM 기반 검색에 유리하게 치우칠 수 있다(순환 편향).
- **대가**: 의미상 관련이 있어도 구조화 속성으로 표현되지 않은 문서는 0점이 된다.
- **재검토**: v2에서 독립적으로 작성한 질의와 사람 판정(pooling)을 도입할 때.

### E-02 '정답' 기준은 등급 2 이상 · 2026-11-05 · 판단

- **근거**: 등급 1은 "카테고리만 맞고 핵심 조건 일부가 다름"이라 구매자 입장에서는 정답이 아니다. 대신 nDCG에는 등급(0~3)을 그대로 넣어 부분 관련성을 반영한다.

### E-03 주 지표는 nDCG@10 · 2026-11-05 · 측정 + 코드

- **측정**: 질의별 정답 수 R은 최소 1, 중앙값 4, 평균 4.9, 최대 22다. R이 10을 넘는 질의가 91개 중 6개다. 이런 질의에서는 Recall@10이 구조적으로 1에 닿을 수 없다. nDCG@10은 이상적인 순위로 정규화하므로 R 차이에 덜 민감하다.
- **@10의 근거**: `vector-search/index.ts`의 기본 `topK = 10`과 맞췄다.

### E-04 질의당 정답 수 상한 25 · 2026-11-05 · 판단

- **근거**: 너무 넓은 질의를 데이터셋 검증 단계에서 걸러내는 안전장치다. 현재 최대값은 22다.
- **실제로 걸린 사례**: q019 "잔존용량 80% 이상 배터리 팩"이 정답 29개로 걸려 85%로 좁혔다.
- **재검토**: 코퍼스 규모를 바꿀 때 비율로 다시 정한다.

### E-05 코퍼스 300개, 질의 91개, v2 목표는 질의 약 350개 · 2026-11-05 · 판단 → 측정

- **v1**: 300개와 100개 안팎은 계획 단계의 판단값이다.
- **측정**: test 44개로 쌍체 비교한 nDCG@10 차이의 95% 신뢰구간 반폭이 **±0.036**이다(`reports/2026-11-05-v1-experiments.json`). 따라서 약 0.035 이하의 개선은 이 데이터셋으로 구분할 수 없다.
- **v2 목표**: 신뢰구간 폭은 1/√n에 비례한다. 반폭을 ±0.018로 줄이려면 test 질의가 약 176개 필요하다. 그래서 dev와 test를 합쳐 약 350개를 목표로 한다.

### E-06 카테고리 분포 (배터리 70, 모터 45, 인버터 35, …) · 2026-11-05 · 판단

- **근거**: 프로젝트의 핵심 품목인 배터리·모터·인버터에 절반(150/300)을 배정했다. 실제 시장의 분포는 아니다.

### E-07 생성 시드 20261105 · 2026-11-05 · 판단

### E-08 회귀 게이트 허용치 0.01 · 2026-11-05 · 측정

- **측정**: BM25 오프라인 실행은 결정적이다. 같은 커밋에서 두 번 실행하면 지표가 같다.
- **계산**: 질의 1개의 nDCG가 1에서 0으로 무너지면 전체 평균은 1/91 ≈ 0.011 떨어진다. 허용치 0.01이면 전체 수준에서 질의 하나의 실패도 잡는다.
- **검증**: 회귀를 일부러 넣었을 때 게이트가 실패했다(exit 1).
- **재검토**: LLM 쿼리 확장처럼 결과가 비결정적인 구성을 게이트에 넣을 때. 그때는 k회 반복 실행의 분산으로 허용치를 다시 정한다.

### E-09 CI 게이트는 BM25만 대상으로 한다 · 2026-11-05 · 공식 제약

### E-11 지표는 직접 구현한다 (ranx 미사용) · 2026-11-05 · 판단

- **근거**: 지표가 nDCG·Recall·MRR·P@k 네 개뿐이다. 이것 때문에 numba 의존성을 추가할 이유가 없다.
- **정확성**: `tests/test_metrics.py`에서 손으로 계산한 값과 비교해 검증한다.

### E-12 시스템 비교는 질의별 쌍체 부트스트랩 CI와 무작위화 검정 · 2026-11-05 · 문헌 + 관행

- **근거**: IR 평가에서는 질의 단위 쌍체 검정이 표준 관행이다. Smucker, Allan, Carterette (CIKM 2007)은 무작위화 검정을 권장했다.
- **반복 횟수**: 10,000회. p = 0.05 근처에서 몬테카를로 표준오차가 약 0.002다.
- **p 표기**: 무작위화 검정의 p는 최소 1/(n+1)이라 "<0.001"로 표기한다.

### E-13 구성은 dev에서 고르고 test에서 확인한다 · 2026-11-05 · 관행

- **근거**: 구성 46개를 같은 질의로 비교한 뒤 최고값을 고르면 그 점수는 과대평가된다(선택 편향).
- **분할 방법**: qtype별로 층화하고, qid의 sha256 순서로 dev와 test를 번갈아 배정한다. 결과는 dev 47개, test 44개다.

### E-14 실험용 BM25는 빠른 구현을 쓰되, 프로덕션 함수와 대조한다 · 2026-11-05 · 측정

- **근거**: 프로덕션 `bm25Score`는 호출할 때마다 문서 빈도를 다시 계산한다. bigram 토크나이저로 46개 구성을 돌리기에는 너무 느리다.
- **검증**: 실행할 때마다 다음 두 가지를 확인하고, 다르면 중단한다.
  - 공백 토크나이저: 프로덕션 `calculateBM25Scores`와 점수 차이 ≤ 1e-9 (질의 4개 × 문서 300개)
  - 후보 20개 구성: 프로덕션 `hybridSearch`와 점수 일치

### E-15 독립 검색 결합에서 min-max의 최대값과 최소값이 같으면 0 · 2026-11-05 · 판단

- **근거**: 정보가 없는 신호는 결합에 기여하지 않게 했다.
- **참고**: 프로덕션 `normalizeBM25Scores`는 이 경우 1을 반환한다. prod 구조 구성은 프로덕션 함수를 그대로 쓴다.

### E-16 결합 기법 후보: 볼록 결합(convex)과 RRF k ∈ {10, 30, 60, 100} · 2026-11-05 · 문헌

- **RRF**: k = 60은 Cormack, Clarke, Büttcher (SIGIR 2009)가 제안한 값이다. 주변 값으로 민감도를 확인한다.
- **볼록 결합**: Bruch, Gai, Ingber (ACM TOIS 2023)는 튜닝한 볼록 결합이 RRF보다 낫다고 보고했다. v1 결과도 같은 방향이다(dev 기준 볼록 결합 0.863, RRF k=30 0.835).

| bigram + 볼록 결합 α=0.7 | +0.031 | | 0.005 |
| IDF 제거 + 볼록 결합 | +0.027 | | 0.005 |
| 현재 구조에서 α만 0.9 | +0.025 | [+0.011, +0.040] | <0.001 |

  - 비교 6개에 Bonferroni 보정(α=0.0083)을 적용해도 위 네 개는 유의하다.
  - 볼록 결합은 α 0.6~0.8에서 dev 0.734~0.738로 거의 같아, α에 민감하지 않다.
  - v1에서 유망했던 **후보 풀 확대는 재현되지 않았다**(+0.004, p=0.63). 이것이 v1을 확정하지 않고 보류한 이유(E-17)가 맞았다는 근거다.
  - RRF는 이번에도 이득이 없었다(−0.002).
- **권고**: 검색을 "BM25(전체 코퍼스)와 벡터를 독립 검색한 뒤 min-max 정규화 볼록 결합(α=0.8)" 구조로 바꾼다.
  - 바꾸기 어려우면 현재 구조에서 α만 0.9로 올린다. 한 줄 변경으로 +0.025다.
  - 적용할 때는 BM25 색인 위치(Lambda 메모리 또는 S3에 직렬화)와 지연 시간을 함께 측정한다.

### E-23 실패 원인 분석: 결합 방식보다 문서 데이터가 더 큰 원인이었다 · 2026-11-05 · 측정

- **방법**: v2 수요 근거 질의 260개에서 현재 하이브리드 상위 5개 중 정답이 아닌 문서를 원인별로 분류했다. 정답 수가 5개보다 적은 질의 때문에 생기는 불가피한 오답은 빼고, 상위 min(5, 정답 수) 자리만 셌다(피할 수 있었던 오답 323건).

| 카테고리는 맞고 대상(차종·양극재·종류) 틀림 | 45% | 54% | 30% |
| 대상은 맞고 수치 사양(용량·SOH·출력) 위반 | 22% | 21% | 15% |

- **원인 1. 결합 가중치가 명목과 달랐다**: 벡터 상위 20개의 코사인 범위가 중앙값 0.164(p10 0.046, p90 0.337)인데, BM25는 후보 안에서 0~1로 펴진다. 범위 기준으로 BM25가 순위의 약 72%를 결정했다(명목 30%). 벡터 단독보다 카테고리 오답이 늘어난 이유다(44 → 69건).
- **원인 2. 검색 문서에 구매자가 찾는 정보가 없거나 틀렸다** (A-21):
  - 가격·연식·수량·상태가 BM25 텍스트에도 임베딩 텍스트에도 없었다.
  - 임베딩 텍스트는 `cycles`·`predictedRange`를 읽었지만 실제 필드는 `cycleCount`·`estimatedMileageKm`이다.
  - 카테고리 단위 고정 키워드가 사실과 다른 정보를 넣었다(SiC 인버터에 IGBT, 유도 모터에 PMSM, 강철 도어에 알루미늄).
  - 운영에서는 BM25가 METADATA만 읽어, SPEC 항목(184개)의 사양이 보이지 않았다.
  - 운영 부품 중 차종이 나오는 90개의 89%(80개)가 영문 표기만 쓴다(`IONIQ 5`). 한글 질의(`아이오닉5`, 실제 검색 기록의 `기아EV`)는 BM25에서 맞을 수 없다.
- **원인 3. 텍스트 검색으로는 부등호 조건을 풀 수 없다**: 수치·거래 조건 위반(33%)은 문서와 결합을 고친 뒤에도 거의 줄지 않았다(수치 사양 72 → 70건). 질의에서 조건을 뽑아 필터로 쓰는 질의 이해가 필요하다. 다음 단계로 둔다.
- **실험** (구성 96개, `reports/2026-11-05-v2-experiments-root-cause.md`). 문서 정의 효과를 검색기별로 분리했다(test nDCG@10).

  - 레거시 모델 차단 사유는 응답 메시지에 그대로 있다: "not actively using the model in the last **30 days**". 프로덕션에 트래픽이 없던 것 자체가 원인이다.

### A-12 Claude 4.7 이후 모델 접근 불가: 원인은 계정 쿼터 0 (처음에는 약정으로 오판) · 2026-11-05 · 측정

> **정정**: 처음에는 이용 약정 미수락을 원인으로 판단했다. 그러나 약정을 수락한 뒤에도 호출이 막혔다. 아래 "쿼터 조사"가 최종 결론이다.

- **증상**: `global.anthropic.claude-haiku-5-5`·`claude-sonnet-5-5` 호출이 `AccessDeniedException: ... is not available for this account`로 실패한다. 4.7 이후 모델과 5.x 모두 같다. Haiku 4.5, Sonnet 4.6, Opus 4.5·4.6은 동작한다.
- **원인** (`bedrock:GetFoundationModelAvailability`, boto3 1.43)

| 모델 | 약정(agreement) | 권한 | 자격 | 리전 |
|---|---|---|---|---|
| Haiku 4.5, Sonnet 4.6 | AVAILABLE | AUTHORIZED | AVAILABLE | AVAILABLE |
| Haiku 5.5, Sonnet 5.5 | **NOT_AVAILABLE** | AUTHORIZED | AVAILABLE | AVAILABLE |

  권한, 자격, 리전 가용성은 모두 갖춰져 있고 **이용 약정만 수락하지 않은 상태**다.
- **해결 방법**: Marketplace offer 약정을 수락한다. 콘솔의 Bedrock 모델 접근 화면이나 `CreateFoundationModelAgreement(modelId, offerToken)`으로 할 수 있다. 현재 IAM 사용자에게 필요한 권한이 있다(`iam simulate-principal-policy` 결과 allowed).
- **약정 조건** (offer 요금표, 1M 토큰당 USD, Global Standard)

| 모델 | 입력 | 출력 |
|---|---:|---:|
| Haiku 5.5 | 0.1 | 0.5 |
| Haiku 4.5 (비교) | 1 | 5 |
| Sonnet 5.5 | 2 | 10 |

  사용량 기반 요금이고 선불 비용은 없다. "No refunds" 조건이 붙어 있다. Haiku 5.5는 Haiku 4.5보다 입출력 단가가 **10배 낮다**.
- **약정 수락 후 (사용자 승인, 2026-11-05)**
  - `CreateFoundationModelAgreement`로 두 모델의 약정을 수락했다. 약 60초 뒤 상태가 AVAILABLE이 됐다.
  - 그 뒤 5분 동안 재시도해도 InvokeModel·Converse 호출은 계속 `not available for this account`였다. **약정은 원인이 아니었다.**
- **실제 원인: 계정 단위 접근 제한**
  - Anthropic 공식 문서("Claude in Amazon Bedrock (Opus 4.7 and later)")에 따르면 4.7 이후 모델은 새 Messages 엔드포인트 `bedrock-mantle`로 제공된다. 접근 기준은 Amazon이 모델별로 정한다. 문서상 Sonnet 5, Opus 4.8, Haiku 4.5는 "모든 고객에게 열림"이고, Haiku 5.5와 Sonnet 5.5는 "See Access"다.
  - 새 엔드포인트를 직접 호출했다(`AnthropicBedrockMantle`, IAM `bedrock-mantle:CreateInference` 허용 확인).

| 리전 | 결과 |
|---|---|
| ap-northeast-2 | Haiku 5.5·Sonnet 5.5·Haiku 4.5: 404 "does not exist" / Sonnet 5: 403 "not available for this account" |
| us-east-1 | Sonnet 5·Haiku 4.5·Opus 4.8 (모두 "열림" 모델): 403 "not available for this account" / Haiku 5.5·Sonnet 5.5: 404 |

  - 결론: 문서상 모든 고객에게 열린 모델까지 막혀 있으므로 **이 계정이 새 엔드포인트를 쓸 수 없는 상태**다. 셀프서비스로 해결할 방법은 찾지 못했다. 커뮤니티(re:Post)에도 같은 증상과 "사용량에 따라 점진적으로 확대된다"는 언급이 있지만, 원문을 열지 못해 2차 출처로만 남긴다.
  - 조치: AWS Support 케이스(Account and billing)로 계정 활성화를 요청한다. 사용자가 진행한다.
  - 영향: 약정은 사용량 기반이라 호출이 없으면 비용이 없다.
- **결정**: 교체 후보는 지금 호출 가능한 ACTIVE 모델인 **Haiku 4.5**(InvokeModel·global profile)와 비교용 **Sonnet 4.6**으로 정한다. 계정이 활성화되면 Haiku 5.5를 같은 평가 절차로 다시 비교한다. Haiku 5.5의 단가는 Haiku 4.5의 1/10이다.
- **쿼터 조사로 확인한 최종 원인** (2026-11-05, Service Quotas `list_service_quotas` / `list_aws_default_service_quotas`, ap-northeast-2·us-east-1 결과 동일)

|---|---:|---:|---|
| Haiku 4.5 | 5,000,000 | 5,000,000 | 됨 |
| Sonnet 4.6 | 6,000,000 | 6,000,000 | 됨 |
| Haiku 5.5 | **0** | 10,000,000 | 막힘 |
| Sonnet 5.5 | **0** | 6,000,000 | 막힘 |
| Sonnet 5, Opus 4.7·4.8·5.5 | **0** | 6M~30M | 막힘 |

  - 동작하는 모델도 분당 요청 수는 기본 10,000이 아니라 **50**으로 낮게 잡혀 있다(A-13).
  - 쿼터 증설 요청에 기본값 이하의 값을 넣으면 "기본값보다 큰 값을 넣어야 한다"며 거부된다. 즉 0은 기본값보다 낮게 조정된 상태가 아니라 **계정에 대한 의도적인 제한**으로 보인다. 사용 이력이 적은 계정에 대한 AWS의 제한으로 추정하지만, 공식 근거는 없다.

  - 그 사이 적용값은 0으로 그대로였고 호출도 계속 거부됐다. 승인되면 A-14 하네스로 Haiku 5.5를 다시 비교한다.

### A-15 지표는 EMF를 stdout에 직접 쓴다 (Powertools 미도입) · 2026-11-05 · 공식 제약 + 판단

- **공식 제약**

### A-21 검색 문서를 하나의 정의로 통일한다 · 2026-11-05 · 측정

- **문제**: 같은 부품을 텍스트로 바꾸는 함수가 네 곳에 따로 있었다. 각자 다른 필드를 읽어서 정보가 조용히 빠졌다(E-23 원인 2).
  - 임베딩: `preparePartText`, BM25: `preparePartForBM25`
  - 스크립트 복사본: `regenerate-vectors.js`, `import-parts-from-json.js`
- **결정**: `utils/search-document.ts`의 `buildSearchText`를 유일한 정의로 둔다. 등록, 재색인, 검색 시점 BM25, 평가가 모두 이것을 쓴다.
  - 원칙: 부품 데이터에서 나온 사실만 넣는다. 코드값은 한국어 표기와 함께 넣는다. 중첩 사양과 등록 폼의 평평한 사양을 모두 읽는다.
  - 임베딩에는 거래 조건 줄을 뺀 `buildEmbeddingText`를 쓴다(E-23 측정).
  - 검색 시점에는 METADATA만 읽으므로, 등록·재색인 때 전체 레코드로 만든 `searchText`와 `searchDocVersion`을 METADATA에 저장한다(비정규화). 버전이 다르면 METADATA로 다시 만든다.
- 이전 함수는 평가 기준선 재현에만 남기고 `@deprecated`로 표시했다.

### A-22 차종·제조사 표기 변형 사전 · 2026-11-05 · 측정 + 판단

- 문서에 나온 표기를 찾아 같은 묶음의 다른 표기를 문서에 덧붙인다(문서 확장). 질의는 바꾸지 않으므로 검색 시점 비용이 없다.
- 부분 문자열이 아니라 단어 1~3개를 이어 붙여 비교한다. "리프트"는 "리프"가 아니다. 뜻이 여럿인 짧은 표기(볼트 = 체결 부품)는 단독으로 넣지 않는다.
- **측정값은 상한이다**: 평가 코퍼스는 문서마다 차종 표기를 바꿔 쓰도록 만들었고(`vehicles.py`), 사전이 그 변형을 대부분 덮는다. 사전의 기여는 BM25 단독 +0.089, 현재 구조 +0.044, 독립 결합 +0.028이다.
- 실제 효과의 독립 근거는 운영 데이터다. 차종이 나오는 부품의 89%가 영문 표기만 쓴다.
- 재검토 조건: 운영 검색 기록이 쌓이면 사전에 없는 표기(결과 0건 질의)를 모아 사전을 보강한다. 사전 변경도 평가 게이트를 통과해야 한다.

### A-23 BM25 색인은 Lambda 메모리에 두고 5분마다 다시 읽는다 · 2026-11-05 · 공식 제약 + 판단

- 독립 BM25에는 전체 코퍼스가 필요하다. 운영 부품은 186개라서 GSI2 쿼리 한 번에 읽는다.
- 벡터 후보 수 100: S3 Vectors QueryVectors 한 페이지가 최대 100건이다(topK 상한은 10,000, 공식 한도). 100이면 페이지 넘김이 없다.
- 유지 시간 5분(판단): 새로 등록한 부품은 벡터 검색에는 바로 잡히고, BM25에는 최대 5분 뒤에 잡힌다. 색인에 없는 부품의 METADATA는 따로 읽는다.
- 검색 단계별 지연(EmbeddingMs, VectorSearchMs, IndexLoadMs, FusionMs, ExplanationMs, TotalMs)을 EMF로 남긴다.
- 재검토 조건: 부품 5,000개 이상이거나 IndexLoadMs p95가 300ms를 넘으면 S3에 직렬화한 색인이나 외부 검색 엔진으로 옮긴다.
  - 관리형 검색 엔진(OpenSearch Serverless)은 이 규모에서 고정 비용이 검색 품질 이득보다 크다고 보고 도입하지 않았다.

### A-24 결과 캐시 키에 필터·topK·파이프라인 버전을 넣는다 · 2026-11-05 · 판단

- 이전 캐시 키는 질의 문자열의 해시뿐이었다. 그래서 필터가 다른 요청에 같은 결과가 나갔다(C-04).
- 또 이대로 배포하면 7일 동안 이전 파이프라인의 결과가 캐시에서 나가, 변경 효과를 운영에서 확인할 수 없다.
- 필터는 상위 topK로 자르기 전에 적용한다(C-05). 이전에는 자른 뒤에 적용해 결과가 줄었다.

### A-25 데이터 모순은 생성기에서 막고, 기존 값은 바꾸지 않는다 · 2026-11-05 · 측정 + 판단

- 운영 배터리 66개 중 12개는 배터리 상태 정보가 없다. 11개는 "신품·최상"인데 SOH가 80% 미만이다(합성 데이터 생성기가 상태와 SOH를 따로 뽑았다). 검색으로는 고칠 수 없는 문제다.
- 생성기에서 SOH 80% 미만이면 신품·최상 등급을 쓰지 않게 했다. 기존 레코드의 상태 값은 판매 정보 자체라서 바꾸지 않고, 재색인 스크립트가 품질 지표로 보고만 한다.
- 재검토 조건: 실제 판매자 등록이 생기면 등록 시 일관성 검증(상태와 SOH, 연식과 차종 출시 연도)을 넣는다.

### A-26 더미 부품 데이터의 모순 정리 · 2026-11-06 · 공식 자료 + 판단

- 운영 데이터는 전부 합성·더미라서 값을 고쳐도 된다(사용자 확인). `backend/scripts/fix-dummy-data-consistency.ts`(dry run 기본)로 44개를 고쳤다.
  - 상태 등급 16개
  - 배터리 상태 보충 12개
  - 출시 전 연식 9개
  - 카테고리 10개
- **상태 등급**(`consistentBatteryCondition`, 판단):
  - new: SOH 98% 이상, 충방전 10회 이하
  - like-new: SOH 95% 이상, 충방전 100회 이하
  - excellent: SOH 90% 이상
  - 맞지 않으면 SOH 구간으로 다시 매긴다: 85% 이상 good, 70% 이상 fair, 그 미만 poor.
  - 70%는 차량용 교체 시점의 하한(통상 70~80%, DEMAND_RESEARCH S4)에서 왔다.
  - 설명 문장의 "새 제품"·"신품" 표현도 함께 고친다. 생성기도 같은 함수를 쓴다.
- **배터리 상태가 없던 12개**:
  - SOH: 설명에 적힌 값(3개)을 쓰고, 없으면 연식으로 추정했다. 추정식은 SOH = 100 − 1.8 × 경과 연수다(Geotab 2024, EV 약 5,000대 분석의 연평균 열화율 1.8%). 추정값에는 `estimated: true`를 남겼다.
  - 양극재·셀 제조사: E-GMP 공개 사양(SK온 NCM)을 썼다.
- **출시 전 연식**: 아이오닉5·EV6(2021년 출시)만 출시 연도로 올렸다. 다른 차종의 연식 검증은 출시 연도표가 없어 하지 않았다.
- **polymer 카테고리 10개**: 재질 분류가 부품 종류 자리에 들어가 구매자 필터에서 보이지 않았다. 부품 이름으로 body-panel·interior·electronics·other로 옮겼다. 재질은 SPEC에 그대로 남는다.
- 재검토 조건: 실제 판매자 등록이 생기면 같은 규칙을 등록 시 검증으로 옮긴다.

### A-27 질의 조건 감점 재정렬과 비교용 속성 저장 · 2026-11-06 · 측정

- 질의에서 카테고리·수치·상태 조건을 뽑아(`query-understanding.ts`) 부품 속성(`search-attributes.ts`)과 비교한다. 위반 1개마다 점수에 0.2를 곱한다(감점 0.8, E-25 dev 선택, E-26 v3 확인).
  - 필터가 아니라 감점이라 결과가 비지 않는다. 확인할 수 없는 조건은 감점하지 않는다.
- BM25 토크나이저는 공백 토큰을 한글 글자 2-gram으로 나눈다(`bigramTokenize`).
- 등록·재색인 때 `searchAttributes`를 METADATA에 저장한다. 검색 문서 정의 버전은 3이다.
  - 용량은 이름의 "72.6kWh"를 쓰고, 없으면 전압 × Ah로 계산한다. 토크는 설명에서 뽑는다.
- 결과에 규칙으로 확인한 `conditions.matched`·`conditions.mismatched`를 함께 돌려준다.
- 알려진 한계: min-max 정규화는 목록이 짧으면 마지막 문서를 0점으로 만든다. 예를 들어 BM25가 두 문서만 맞추면, 아래 문서의 BM25 기여는 0이다.

### A-28 결과 설명 프롬프트가 적합하다는 결론을 전제하지 않게 한다 · 2026-11-06 · 운영 관측

- 이전 프롬프트는 "왜 적합한지 '~이므로 적합' 형식으로" 쓰게 했다. 그래서 조건에 맞지 않는 부품에도 이유를 지어냈다.
  - 운영 확인 예: Model 3 언더커버에 "Model 3 모터 성능 향상에 필요한 보조 부품", IONIQ Electric 배터리에 "아이오닉5와 동일 차종".
- 이제 규칙으로 확인한 일치·불일치를 부품별로 주고, 불일치를 먼저 쓰게 한다. 근거가 없으면 "조건 확인 필요"라고 쓰게 한다.
- 남은 문제: 설명은 여전히 응답 시간의 81%다(C-08). 다음 단계에서 응답 경로와 분리한다.

### A-29 운영 순위 로직을 CI 게이트에 넣는다 (게이트용 임베딩 커밋) · 2026-11-06 · 측정 + 판단

- CI 게이트는 비용 때문에 BM25 단독만 검사했다. 그런데 이번 변경에서 BM25 단독은 일부 그룹이 떨어졌고, 운영 파이프라인은 모든 그룹이 올랐다.
  - BM25 단독 하락 예: v1 mixed nDCG 0.671 → 0.612, v1 recall@10 0.884 → 0.862, v2 F-conversion 0.675 → 0.631
  - 운영 파이프라인: v2 0.776 → 0.876, v1 0.882 → 0.935
- 즉 게이트가 운영과 다른 대상을 재고 있었다. BM25 단독 기준값은 의도한 변경으로 갱신하고, 운영 순위 게이트(prod-hybrid, v2·v3)를 추가한다.
- 질의 벡터와 현재 문서 벡터만 gzip으로 묶어 `datasets/<v>/gate-embeddings.json.gz`로 커밋한다. 크기는 v2 1.8MB, v3 1.3MB다. CI에 AWS 자격 증명이 필요 없다.
- 묶음에는 문서 텍스트 해시(`docTextSha256`)가 들어 있다. 문서 정의가 바뀌면 게이트가 "임베딩을 다시 만들라"며 실패한다.
- 재검토 조건: 저장소 크기가 문제가 되면(묶음 갱신이 잦아지면) Git LFS나 CI 캐시 아티팩트로 옮긴다.

### A-30 결과 설명을 검색 응답과 분리한다 · 2026-11-06 · 측정

- 운영 v1.7.0에서 설명이 응답 시간의 83%였다(평균 1,538ms / 1,850ms, EMF). 검색 순위 계산은 평균 6ms다.
- 검색 요청에 `explain=false`를 주면 LLM 없이 바로 응답한다. `reason`에는 규칙으로 확인한 조건 요약을 넣는다(`summarizeCheck`, 예: "조건 불일치: 용량 17.6kWh (일치: 카테고리)"). 그리고 `reasonSource: 'rules'`로 표시한다.
- 설명은 `POST /api/search/explain {query, partIds}`로 따로 받는다(같은 Lambda, 최대 20개, 7일 캐시). 폴백 설명은 캐시하지 않는다.
- 프론트엔드는 결과를 먼저 보여 주고, 화면에 보이는 결과의 설명만 요청해 채운다.
- 결과 카드의 "87% 일치" 배지는 목록 안 상대 점수(score)에 100을 곱한 값이었다. 일치도가 아니고 1위는 거의 항상 100%다. 그래서 규칙으로 확인한 "조건 n/m 일치"로 바꿨다.
- `explain` 기본값은 true로 두어 기존 클라이언트는 그대로 동작한다. 캐시 키에 explain을 넣었다.

### A-31 프론트엔드 커버리지 임계값은 적용된 적이 없었다 · 2026-11-06 · 측정

- `vitest.config.ts`는 `thresholds: { global: {...70} }`로 적혀 있었다. `global`은 Jest 문법이라 Vitest 4가 무시했다. 문서(CLAUDE.md)의 "커버리지 70%"는 프론트엔드에서 한 번도 검사되지 않았다.
- 올바른 문법으로 고치면 현재 커버리지(구문 27.9%, 분기 18.4%, 함수 18%, 줄 29.4%)에서 바로 실패한다.
- 결정: 문법을 고치고 **현재값을 하한으로 고정**한다(구문 27, 분기 18, 함수 18, 줄 29). 검사가 없던 상태보다 엄격하다. 커버리지를 올리면 하한도 함께 올린다.
- 백엔드(Jest)의 70%는 실제로 적용되고 있다(현재 약 93%).

### A-32 차종 사전을 운영 DB의 차종으로 보강한다 · 2026-11-06 · 측정

- v1.8.0 운영 확인에서 "테슬라 모델3 모터"의 1위가 ID.3 모터였다. ID.3가 사전에 없어 차종을 판단하지 못했다.
- 운영 부품 186개 중 사전이 차종을 알아본 부품은 90개(48%)뿐이었다. 사전에 없는 차종은 70종이다. 평가 코퍼스는 사전에 있는 22개 차종만 써서 이 문제가 드러나지 않았다.
- 운영 DB의 브랜드·모델 110종으로 사전을 보강하고, `vehicleBrand` + `model`도 함께 보게 했다. 판정 비율은 **48% → 96%(178/186)**다.
  - 남은 8개는 "EV Universal"(범용) 6개와 모델명이 빈 2개다. 판정하지 않는 것이 맞다.
- 짧고 다른 뜻과 겹치는 표기(BYD "Han" = 한, Rivian "R3", Lucid "Air", XPeng "G6")는 브랜드와 함께만 넣었다.
- 평가 코퍼스의 문서 텍스트는 바뀌지 않았다(게이트 묶음 해시 일치, 모든 게이트 통과).
- 사전이 저장 속성에 영향을 주므로 검색 문서 정의 버전을 5로 올렸다. 배포 후 재색인이 필요하다.

### A-33 운영 데이터 회귀 검사를 CI에 둔다 · 2026-11-06 · 측정

- 합성 평가 코퍼스에는 운영의 실패 유형(붙여 쓴 표기, 사전에 없는 차종, 운영 데이터의 이름 형식)이 잘 나타나지 않는다(E-27).
- 운영 부품 186개의 원본 레코드를 스냅숏(`datasets/prod-snapshot`, 전부 더미 데이터)으로 커밋했다. `eval/prod/regression.json`의 검사 16개를 프로덕션 순위 함수로 실행한다(`eval/ts/prod-regression.ts`, AWS 불필요).
  - 검색 문서·속성은 원본 레코드로 현재 코드가 다시 만든다. 문서 벡터도 현재 코드의 임베딩 텍스트로 만들고, 텍스트 해시가 다르면 실패한다.
- 검사는 관찰된 실패(아이오닉5 → IONIQ Electric, 모델3 모터 → 언더커버, 60kWh 이상 → 17.6kWh)와 기본 조건 질의(가격·연식·SOH·카테고리·차종)다.
- **검사가 회귀를 잡는지 확인**: 조건 재정렬을 끈 구조(v1.6.0에 가까움)에서는 8/16만 통과한다. 현재 구조는 16/16이다.

### A-36 Slack 이벤트 즉시 응답과 비동기 처리 · 2026-11-06 · 공식 제약 + 판단

- **공식 제약**: Slack Events API와 슬래시 커맨드는 3초 안에 HTTP 200을 받아야 한다. 받지 못하면 Events API는 최대 3번 재시도한다(`X-Slack-Retry-Num`). 슬래시 커맨드는 `response_url`로 30분 안에 지연 응답을 보낼 수 있다.
- **이전 문제** (코드에서 확인)
  - ReAct 루프(평가 기준 평균 5~8초)를 끝낸 뒤 200을 돌려줘 3초를 넘겼다.
  - 재시도는 서명 검증 전에 일괄로 버렸다. 그래서 첫 요청이 콜드 스타트나 오류로 실패하면 그 이벤트는 처리되지 않았다.
  - 요청 전체(서명 헤더, 사용자 메시지)를 INFO 로그로 남겼다.
- **변경 (C-13)**
  - 수신 경로는 서명 검증 → `event_id` 선점 → 같은 함수 비동기 호출(`InvocationType: Event`) → 200만 한다. 재시도도 서명부터 검증한다.
  - 무거운 슬래시 커맨드도 비동기로 넘기고 결과는 `response_url`로 보낸다. 외부 조회가 없는 도움말만 즉시 응답한다.
  - 큐(SQS)를 두지 않고 Lambda 비동기 호출을 썼다. Lambda 비동기 호출은 내부 큐가 있고, 대화형 요청 한 건을 처리하는 데 순서 보장이나 배치가 필요 없다(판단). 처리량이 늘거나 실패 작업을 다시 돌려야 하면 SQS로 바꾼다.
- **중복 처리 방지**: `event_id`를 DynamoDB 조건부 쓰기(`attribute_not_exists`)로 선점한다. 이미 있으면 재시도·중복 전달로 보고 처리하지 않는다.
  - 기록 유지는 하루(TTL)다. Slack 재시도는 몇 분 안에 끝나므로 넉넉한 값이다(판단).
  - 저장소 장애 시에는 처리한다(fail open). 답이 두 번 가는 것이 답이 안 가는 것보다 낫다는 판단이며, 알림 중복 제거와 같은 선택이다(A-03).
- **비동기 호출 자동 재시도를 막는다**: Lambda는 함수 오류가 나면 비동기 호출을 두 번 더 재시도한다(공식 동작). 작업이 중간에 실패한 뒤 재시도하면 Slack에 답이 두 번 갈 수 있다. 실패는 사용자가 다시 물으면 된다(판단).
  - 처음에는 `EventInvokeConfig: MaximumRetryAttempts: 0`으로 막으려 했다. v1.9.0 배포가 배포 역할 권한 부족(`lambda:PutFunctionEventInvokeConfig`)으로 실패하고 자동 롤백됐다(운영은 v1.8.1 유지).
  - 배포 역할 권한을 늘리는 대신 **작업 경로가 예외를 던지지 않게** 했다. 함수 오류가 없으면 재시도도 없다. 이 방식이 권한 변경 없이 같은 목적을 이룬다.
  - 대가: 예외를 삼키므로 Lambda `Errors` 지표에 잡히지 않는다. 그래서 `JobErrors`(차원 `JobType`)를 따로 남긴다.
  - 남는 재시도: 제한 시간 초과·런타임 장애는 여전히 재시도된다. 이때는 첫 시도가 답을 보내기 전에 끊겼을 가능성이 높아(전송이 마지막 단계) 재시도가 낫다고 봤다(판단).
- **자기 호출 권한**: 함수가 자기 ARN을 `!GetAtt`로 참조하면 순환 의존이 된다. 그래서 `${AWS::StackName}-SlackAgentFunction-*` 접두사로 범위를 한정했다.
- **검증 지표**: `SlackAckLatency`(수신부터 응답까지), `SlackRetries`, `SlackDuplicates`(차원 `Ingress`), `JobErrors`(차원 `JobType`). 기대값은 응답 시간 3초 미만, 재시도 수신이 있으면 중복으로 걸러진 수와 같아야 한다.
- **배포 전후 측정** (서명한 테스트 요청, 클라이언트에서 잰 왕복 시간. 결과는 존재하지 않는 채널로 보내 Slack에 올라가지 않음)

| 요청 | v1.8.1 (동기) | v1.9.1 |
|---|---:|---:|
| `분석` 슬래시 커맨드 | 5,640ms | 120ms |
| @멘션 | 3,918ms | 194ms |
| 같은 `event_id` 재전송 | 3,565ms, 에이전트 다시 실행 | 47ms, 중복으로 걸러짐 |
| `help` (콜드 / 웜) | 1,119 / 50ms | 91 / 49ms |

  - 함수 안에서 잰 `SlackAckLatency`는 0~63ms다. 비동기 작업은 실행됐다(에이전트 2턴, $0.0085, 3.4초).
  - 요청 로그에는 크기만 남고 이벤트 전체는 남지 않는다.
- 재검토 조건: 수신 응답 p99가 1초를 넘으면(콜드 스타트 포함) 수신 함수와 작업 함수를 나누거나 프로비저닝 동시성을 검토한다.

### A-37 부품 등록 함수의 S3 Vectors 쓰기 권한 누락 · 2026-11-06 · 측정

- `PartRegistrationFunction` 역할에 `s3vectors:PutVectors`가 없었다. 새 부품의 벡터 업로드는 AccessDenied로 실패했다.
- 등록 코드는 이 오류를 잡아 로그만 남겼다. 그래서 등록 자체는 성공하고, 새 부품은 BM25로만 검색됐다. 합성 데이터 함수에는 이 권한이 있고 일괄 스크립트(`regenerate-vectors.js`)로도 벡터를 넣을 수 있어, 등록 API로 넣은 부품만 빠져 드러나지 않았다.
- 발견 경위: 자동이 홀드아웃 시나리오를 쓰던 에이전트가 코드와 템플릿을 대조하다 찾았다(h01의 부차 원인으로 들어감).
- 수정: 대상 버킷과 `parts-vectors` 색인에만 `PutVectors`를 허용했다. 같은 역할의 `lambda:InvokeFunction`은 `Resource: '*'`였는데, 실제로 호출하는 `ComplianceCheckFunction`으로 좁혔다(최소 권한).
- **확인 (v1.9.1)**: 등록 API로 테스트 부품을 넣었다. 등록 로그에 `Vector uploaded to S3 Vectors`가 남았고, `GetVectors`로 키와 메타데이터를 조회했다. 테스트 항목(DynamoDB, S3 Vectors, 레거시 벡터 JSON, 매니페스트 항목)은 모두 지웠다.
- 같이 발견한 것: 레거시 벡터 매니페스트에 실제 파일이 없는 항목이 4개 있다. 레거시 경로는 롤백용이라 고치지 않았다.

### A-41 조용한 실패와 잘못된 분류 수정 · 2026-11-06 · 코드 확인 + 판단

- **경위**: 시나리오 v3를 작성한 에이전트가 코드를 보다가 발견해 보고했다. 시나리오와 별개로 코드에서 하나씩 사실을 확인한 뒤 고쳤다.
- **검색어 원문을 로그에 남기지 않는다**
  - 이전에는 `console.log('Processing search query:', query)`였다. 구독 필터가 `?ERROR ?Exception ?Timeout ?"Task timed out"`이므로 검색창에 `ERROR`를 넣으면 누구나 알림을 만들 수 있었다.
  - 같은 문자열이 자동이의 로그 조회 결과로도 들어간다. 외부 입력이 에이전트 컨텍스트로 흘러가는 경로(프롬프트 인젝션)다.
  - 이제 길이와 캐시 해시만 남긴다. 다른 함수에는 원문을 그대로 찍는 곳이 없음을 확인했다.
  - 재검토 조건: 검색어 분석이 필요해지면 구독 필터 대상이 아닌 별도 저장소에 익명으로 남긴다.
- **캐시 적중 수를 원자적으로 올리고, 실패해도 응답을 깨지 않는다**
  - 이전에는 항목을 읽어 전체를 덮어썼다. 동시 요청이 수를 잃었고, 쓰기 스로틀이 나면 이미 찾은 캐시 결과가 500이 됐다.
  - 이제 `ADD hitCount :by`로 올리고, 실패는 `console.warn`만 남긴다. `console.error`는 필터에 걸리고, 통계 실패는 사용자에게 영향이 없다.
  - `GSI1SK`(`HIT_COUNT#n`)는 더 이상 갱신하지 않는다. 코드에서 읽는 곳이 없고, 숫자를 0으로 채우지 않은 문자열이라 정렬도 맞지 않았다(`9` > `10`). `hitCount` 값을 쓴다.
- **이상한 레코드 하나가 BM25 색인 전체를 실패시키지 않는다**
  - 문자열이 아닌 `cathodeType` 하나로 `toUpperCase` 예외가 나 전체 적재가 실패했다. 값 처리를 고치고, 그 밖의 예외도 해당 레코드만 건너뛰고 건수를 경고로 남긴다.
  - 건너뛴 부품은 검색에서 빠진다. 전체 실패보다 낫지만 조용하면 안 되므로 경고를 남긴다. 합성 검사가 색인 100개 이상을 확인한다(A-39).
- **규정 검사: 모델 실패를 "위반 없음"으로 처리하지 않는다**
  - 이전에는 모델 호출이 실패하면 빈 목록을 돌려줘 `No compliance violations found`로 기록했다. 규정 검사가 꺼져도 알 수 없었다.
  - 이제 `null`을 돌려주고 `console.error` + EMF `EECAR/Compliance ComplianceCheckFailed`를 남긴다. 등록을 막지는 않는다(기존 설계대로 비핵심 경로).
  - "위반 사항 없음"을 위반으로 세던 파싱도 고쳤다(`parseViolations`).
- **알림 분류: 예외 이름이 아니라 메시지 내용으로 서비스를 가린다**
  - 이전에는 모든 `ThrottlingException`·`AccessDeniedException`을 Bedrock으로 표시했고, 모든 `ValidationException`을 DynamoDB로 표시했다. 이 값은 알림의 심각도와 자동이의 첫 판단에 쓰인다.
  - 권한 오류는 `perform: dynamodb:PutItem`의 액션 접두사로 판별한다(공식 오류 형식). 스로틀·검증 오류의 문구 규칙은 판단이다. 어느 쪽에도 맞지 않으면 서비스를 지어내지 않고 `Throttling`·`AccessDenied`·`ValidationError`로 둔다.
  - 스택 줄은 판별에서 뺀다. 테스트가 `/var/runtime/index.js`의 `index`를 DynamoDB로 읽는 오류를 잡았다.
  - 재검토 조건: 실제 알림에서 `Throttling`·`AccessDenied`·`ValidationError`로 남는 비율이 높으면 그 문구를 규칙에 추가한다.
- **배포 전후 측정 (v1.10.0 → v1.10.1, 2026-11-06)**

  | 항목 | 배포 전 | 배포 후 |
  |---|---|---|
  | 검색어 원문 로그 줄 | 24시간에 50줄 | 0줄 (배포 후 약 2분, 검색 9건) |
  | `ERROR Exception`이 든 검색어 3회의 구독 필터 일치 | 코드상 일치 (일부러 보내지 않음) | 0줄 |
  | 그 뒤 알림 함수 로그 | 측정 안 함 | 0건 |
  | 같은 검색 3회의 `hitCount` | 측정 안 함 | 3 (생성 1 + 적중 2), 응답 200 |
  | 합성 검사 | 통과 | 통과 |

  - 배포 후 구간이 짧다. 일정 실행이 쌓이면 원문 줄이 계속 0인지 다시 본다.
  - 규정 검사 실패 지표, 알림 분류, 이상 레코드 건너뛰기는 해당 오류가 운영에서 나야 동작한다. 단위 테스트로만 확인했다.
- **고치지 않은 것**: `S3_VECTORS_BUCKET`이 비면 레거시 경로로 조용히 폴백한다. 템플릿이 값을 항상 넣어 현재 발생하지 않는다. 합성 검사의 벡터 후보 수 검사가 이 경우도 잡는다.

### A-42 복잡한 질문용 모델이 스로틀되면 기본 모델로 답한다 · 2026-11-06 · 측정 + 판단

- **발견**: 평가 판정 모델을 돌리다 Sonnet 4.6이 `ThrottlingException: Too many tokens per day`를 냈다.
  - 그날 Sonnet 4.6 사용량(CloudWatch `AWS/Bedrock`): 입력 약 935만 + 출력 약 67만 = 약 1,001만 토큰.
  - Service Quotas에는 이 모델의 일일 토큰 항목이 없다(분당 요청 50, 분당 토큰 600만만 있다). 약 1,000만은 공시값이 아니라 **관측값**이다. 한 번 관측했고, 초기화 시각도 아직 모른다.
  - Haiku 4.5는 같은 날 약 1,937만 토큰까지 스로틀이 없었다. 상한은 모른다.
- **영향**: 자동이는 "분석해", "원인 뭐" 같은 질문의 첫 턴에 Sonnet을 쓴다. 한도에 닿아 있는 동안 이런 질문은 `죄송합니다, 처리 중 오류가 발생했습니다.`로 끝난다. 이번 한도는 평가 실행이 소진했다.
- **회복 관측**: 한도 오류 약 40분 뒤 Sonnet 작은 요청(약 6천 토큰)이 성공했다. 고정 시각 초기화보다는 조금씩 회복되는 방식으로 보이지만 한 번의 관측이다. 회복 속도는 모른다.
- **수정**: Sonnet이 `ThrottlingException`이면 같은 요청을 기본 모델(Haiku)로 한 번 다시 보낸다. 복잡한 답의 품질은 떨어질 수 있지만, 답이 없는 것보다 낫다(판단).
  - 다른 오류는 그대로 처리한다. 권한 오류를 다른 모델로 재시도해도 원인을 가릴 뿐이다.
  - `modelOverride`가 있으면 폴백하지 않는다. 평가는 지정한 모델을 재야 한다.
  - EMF `AgentModelFallbacks`와 로그 `eecar.agent.model_fallbacks`로 남긴다.
- **평가 운영 규칙**: 평가는 운영과 같은 계정 할당량을 쓴다. 판정 모델(Sonnet)은 하루 약 600만 토큰 안에서 계획하고, 큰 실행은 한 건마다 저장해 이어서 돌린다.
- **확인 범위**: 폴백 조건의 오류 이름은 판정 실행이 멈출 때 남긴 실제 오류(`ThrottlingException: Too many tokens per day`)와 일치한다. 폴백 동작 자체는 단위 테스트로만 확인했다. 시험 시점에는 한도가 이미 회복돼 실제 폴백을 재현하지 못했다.
- 재검토 조건: 한도의 회복 방식이나 공식 값을 확인하면 이 기록을 고친다. 폴백이 자주 나오면 평가와 운영의 할당량을 분리한다(계정 분리 또는 쿼터 상향).

### A-43 합성 검사 경보를 이메일로 연결하고 일정을 다시 등록한다 · 2026-11-06 · 측정 + 판단

### A-47 공개 API 호출 제한, 합성 검사 토큰, 설명 LLM 하루 상한 · 2026-11-09 · 측정 + 판단

- **문제**: 검색 API에는 인증이 없고 스테이지 호출 제한도 없었다. `canary=true`는 본문 값만 보고 캐시를 건너뛰어, 누구나 매번 LLM 설명을 부르고 내부 진단값(색인 크기, 후보 수)을 받을 수 있었다.
- **측정 (2026-11-09 CloudWatch)**: 최근 14일 요청 236건, 시간당 최대 20건. 최근 24시간 분당 최대 7건(초당 0.12건). 검색 Lambda p50 264ms, p99 2.83초, 최대 5.97초. 설명 생성 평균 1.66초, 최대 5.76초. 계정 Lambda 동시 실행 한도 10. 설명 LLM 호출은 하루 최대 29건, 보통 3~5건.
- **호출 제한 (`MethodSettings`, 판단)**

  | 경로 | 초당 | 버스트 | 정한 이유 |
  |---|---:|---:|---|
  | 전체 기본 | 10 | 20 | 관측 최대 초당 0.12건의 약 80배 |
  | `POST /api/search` | 2 | 5 | p99 2.83초 기준 동시 실행 약 5.7 |
  | `POST /api/search/explain` | 1 | 3 | 최대 5.76초 기준 동시 실행 약 5.8 |

  - 평균 지연으로 두 경로가 함께 포화되면 동시 실행은 약 3.5다. 전부 최악 지연이면 약 11.4로 한도 10을 넘을 수 있지만, 그 경우 Lambda가 스로틀되어 비용은 늘지 않는다.
  - **한계**: 이 값은 모든 클라이언트가 공유한다. 한 사용자가 소진하면 다른 사용자도 429를 받는다. 클라이언트별 제한은 WAF rate-based rule이 필요한데, 웹 ACL과 규칙에 월 고정 비용이 있어 월 예산 $10을 넘긴 지금은 넣지 않는다. 429 응답에는 CORS 헤더가 없어 브라우저에서는 네트워크 오류로 보이고, 프론트엔드의 기존 실패 처리로 간다.
  - 재검토 조건: 실제 남용이 관측되거나, 시간당 요청이 현재 최대의 10배(200건)를 넘으면 값과 WAF 도입을 다시 본다.
- **합성 검사 토큰 (판단)**: `canary=true`는 `X-Eecar-Canary-Token` 헤더가 SSM `/eecar/canary-token`(SecureString)과 맞을 때만 적용한다. 토큰은 Lambda에 5분 캐시하고, 해시를 일정 시간 비교한다.
  - 토큰이 없거나 틀리면, 또는 SSM을 읽지 못하면 403 대신 일반 요청으로 처리한다. 배포 순서와 무관하게 사용자 요청이 깨지지 않고, 토큰을 읽지 못하면 진단값이 비어 합성 검사가 실패로 알린다.
  - 헤더가 없는 요청은 SSM을 읽지 않는다. 틀린 토큰으로 SSM 호출을 늘릴 수 없도록 값을 캐시한다.
  - 토큰을 바꾸면 최대 5분 동안 합성 검사가 실패할 수 있다.
- **설명 LLM 하루 상한 200건 (판단)**: 호출 제한만으로는 설명 요청이 하루 86,400건까지 통과한다. Haiku 4.5($1/$5 per MTok)로 부품 20개, 출력 상한 1,800토큰이면 호출당 최대 약 $0.011이라 하루 약 $950까지 가능했다. 상한 200건이면 최대 약 $2.2다. 관측 최대 29건의 약 7배다.
  - 상한에 도달하면 LLM을 부르지 않고 기존 폴백 문구로 응답한다. `LLMFallback` 경보와 합성 검사 실패로 Slack에 알려진다.
  - 카운터가 실패하면 설명은 그대로 진행한다. 호출 제한이 순간 부하를 막고, 비용 방어보다 기능 유지를 앞세웠다.
  - 재검토 조건: 실제 호출이 하루 100건을 넘거나, 상한 도달 경보가 정상 사용 때문에 울리면 값을 올린다.
