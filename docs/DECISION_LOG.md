# 결정 기록 (Decision Log)

수치, 임계값, 기법을 정하거나 바꿀 때마다 여기에 기록한다. 항목마다 **근거 유형**을 표시한다.

| 근거 유형 | 뜻 |
|---|---|
| 측정 | 이 저장소나 운영 환경에서 직접 측정한 값 (재현 방법 포함) |
| 공식 제약 | AWS·라이브러리 문서에 정해진 한도나 호환 범위 |
| 문헌 | 논문이나 널리 인용되는 자료 |
| 관행 | 업계에서 일반적으로 쓰는 방식 |
| 판단 | 근거 없이 정한 값. **재검토 조건을 반드시 적는다** |

## 평가 하네스 (`eval/`)

### E-01 정답 등급은 규칙으로 판정한다 (LLM 판정 미사용) · 2026-11-05 · 판단

- **근거**: 코퍼스와 질의를 LLM으로 만들었다. 판정까지 LLM에 맡기면 LLM 기반 검색에 유리하게 치우칠 수 있다(순환 편향).
- **대가**: 의미상 관련이 있어도 구조화 속성으로 표현되지 않은 문서는 0점이 된다.
- **재검토**: v2에서 독립적으로 작성한 질의와 사람 판정(pooling)을 도입할 때.

### E-02 '정답' 기준은 등급 2 이상 · 2026-11-05 · 판단

- **근거**: 등급 1은 "카테고리만 맞고 핵심 조건 일부가 다름"이라 구매자 입장에서는 정답이 아니다. 대신 nDCG에는 등급(0~3)을 그대로 넣어 부분 관련성을 반영한다.

### E-03 주 지표는 nDCG@10 · 2026-11-05 · 측정 + 코드

- **측정**: 질의별 정답 수 R은 최소 1, 중앙값 4, 평균 4.9, 최대 22다. R이 10을 넘는 질의가 91개 중 6개다. 이런 질의에서는 Recall@10이 구조적으로 1에 닿을 수 없다. nDCG@10은 이상적인 순위로 정규화하므로 R 차이에 덜 민감하다.
- **@10의 근거**: `vector-search/index.ts`의 기본 `topK = 10`과 맞췄다.

### E-04 질의당 정답 수 상한 25 · 2026-11-05 · 판단

- **근거**: 너무 넓은 질의를 데이터셋 검증 단계에서 걸러내는 안전장치다. 현재 최대값은 22다.
- **실제로 걸린 사례**: q019 "잔존용량 80% 이상 배터리 팩"이 정답 29개로 걸려 85%로 좁혔다.
- **재검토**: 코퍼스 규모를 바꿀 때 비율로 다시 정한다.

### E-05 코퍼스 300개, 질의 91개, v2 목표는 질의 약 350개 · 2026-11-05 · 판단 → 측정

- **v1**: 300개와 100개 안팎은 계획 단계의 판단값이다.
- **측정**: test 44개로 쌍체 비교한 nDCG@10 차이의 95% 신뢰구간 반폭이 **±0.036**이다(`reports/2026-11-05-v1-experiments.json`). 따라서 약 0.035 이하의 개선은 이 데이터셋으로 구분할 수 없다.
- **v2 목표**: 신뢰구간 폭은 1/√n에 비례한다. 반폭을 ±0.018로 줄이려면 test 질의가 약 176개 필요하다. 그래서 dev와 test를 합쳐 약 350개를 목표로 한다.

### E-06 카테고리 분포 (배터리 70, 모터 45, 인버터 35, …) · 2026-11-05 · 판단

- **근거**: 프로젝트의 핵심 품목인 배터리·모터·인버터에 절반(150/300)을 배정했다. 실제 시장의 분포는 아니다.

### E-07 생성 시드 20261105 · 2026-11-05 · 판단

### E-08 회귀 게이트 허용치 0.01 · 2026-11-05 · 측정

- **측정**: BM25 오프라인 실행은 결정적이다. 같은 커밋에서 두 번 실행하면 지표가 같다.
- **계산**: 질의 1개의 nDCG가 1에서 0으로 무너지면 전체 평균은 1/91 ≈ 0.011 떨어진다. 허용치 0.01이면 전체 수준에서 질의 하나의 실패도 잡는다.
- **검증**: 회귀를 일부러 넣었을 때 게이트가 실패했다(exit 1).
- **재검토**: LLM 쿼리 확장처럼 결과가 비결정적인 구성을 게이트에 넣을 때. 그때는 k회 반복 실행의 분산으로 허용치를 다시 정한다.

### E-09 CI 게이트는 BM25만 대상으로 한다 · 2026-11-05 · 공식 제약

### E-11 지표는 직접 구현한다 (ranx 미사용) · 2026-11-05 · 판단

- **근거**: 지표가 nDCG·Recall·MRR·P@k 네 개뿐이다. 이것 때문에 numba 의존성을 추가할 이유가 없다.
- **정확성**: `tests/test_metrics.py`에서 손으로 계산한 값과 비교해 검증한다.

### E-12 시스템 비교는 질의별 쌍체 부트스트랩 CI와 무작위화 검정 · 2026-11-05 · 문헌 + 관행

- **근거**: IR 평가에서는 질의 단위 쌍체 검정이 표준 관행이다. Smucker, Allan, Carterette (CIKM 2007)은 무작위화 검정을 권장했다.
- **반복 횟수**: 10,000회. p = 0.05 근처에서 몬테카를로 표준오차가 약 0.002다.
- **p 표기**: 무작위화 검정의 p는 최소 1/(n+1)이라 "<0.001"로 표기한다.

### E-13 구성은 dev에서 고르고 test에서 확인한다 · 2026-11-05 · 관행

- **근거**: 구성 46개를 같은 질의로 비교한 뒤 최고값을 고르면 그 점수는 과대평가된다(선택 편향).
- **분할 방법**: qtype별로 층화하고, qid의 sha256 순서로 dev와 test를 번갈아 배정한다. 결과는 dev 47개, test 44개다.

### E-14 실험용 BM25는 빠른 구현을 쓰되, 프로덕션 함수와 대조한다 · 2026-11-05 · 측정

- **근거**: 프로덕션 `bm25Score`는 호출할 때마다 문서 빈도를 다시 계산한다. bigram 토크나이저로 46개 구성을 돌리기에는 너무 느리다.
- **검증**: 실행할 때마다 다음 두 가지를 확인하고, 다르면 중단한다.
  - 공백 토크나이저: 프로덕션 `calculateBM25Scores`와 점수 차이 ≤ 1e-9 (질의 4개 × 문서 300개)
  - 후보 20개 구성: 프로덕션 `hybridSearch`와 점수 일치

### E-15 독립 검색 결합에서 min-max의 최대값과 최소값이 같으면 0 · 2026-11-05 · 판단

- **근거**: 정보가 없는 신호는 결합에 기여하지 않게 했다.
- **참고**: 프로덕션 `normalizeBM25Scores`는 이 경우 1을 반환한다. prod 구조 구성은 프로덕션 함수를 그대로 쓴다.

### E-16 결합 기법 후보: 볼록 결합(convex)과 RRF k ∈ {10, 30, 60, 100} · 2026-11-05 · 문헌

- **RRF**: k = 60은 Cormack, Clarke, Büttcher (SIGIR 2009)가 제안한 값이다. 주변 값으로 민감도를 확인한다.
- **볼록 결합**: Bruch, Gai, Ingber (ACM TOIS 2023)는 튜닝한 볼록 결합이 RRF보다 낫다고 보고했다. v1 결과도 같은 방향이다(dev 기준 볼록 결합 0.863, RRF k=30 0.835).

| bigram + 볼록 결합 α=0.7 | +0.031 | | 0.005 |
| IDF 제거 + 볼록 결합 | +0.027 | | 0.005 |
| 현재 구조에서 α만 0.9 | +0.025 | [+0.011, +0.040] | <0.001 |

  - 비교 6개에 Bonferroni 보정(α=0.0083)을 적용해도 위 네 개는 유의하다.
  - 볼록 결합은 α 0.6~0.8에서 dev 0.734~0.738로 거의 같아, α에 민감하지 않다.
  - v1에서 유망했던 **후보 풀 확대는 재현되지 않았다**(+0.004, p=0.63). 이것이 v1을 확정하지 않고 보류한 이유(E-17)가 맞았다는 근거다.
  - RRF는 이번에도 이득이 없었다(−0.002).
- **권고**: 검색을 "BM25(전체 코퍼스)와 벡터를 독립 검색한 뒤 min-max 정규화 볼록 결합(α=0.8)" 구조로 바꾼다.
  - 바꾸기 어려우면 현재 구조에서 α만 0.9로 올린다. 한 줄 변경으로 +0.025다.
  - 적용할 때는 BM25 색인 위치(Lambda 메모리 또는 S3에 직렬화)와 지연 시간을 함께 측정한다.

### E-23 실패 원인 분석: 결합 방식보다 문서 데이터가 더 큰 원인이었다 · 2026-11-05 · 측정

- **방법**: v2 수요 근거 질의 260개에서 현재 하이브리드 상위 5개 중 정답이 아닌 문서를 원인별로 분류했다. 정답 수가 5개보다 적은 질의 때문에 생기는 불가피한 오답은 빼고, 상위 min(5, 정답 수) 자리만 셌다(피할 수 있었던 오답 323건).

| 카테고리는 맞고 대상(차종·양극재·종류) 틀림 | 45% | 54% | 30% |
| 대상은 맞고 수치 사양(용량·SOH·출력) 위반 | 22% | 21% | 15% |

- **원인 1. 결합 가중치가 명목과 달랐다**: 벡터 상위 20개의 코사인 범위가 중앙값 0.164(p10 0.046, p90 0.337)인데, BM25는 후보 안에서 0~1로 펴진다. 범위 기준으로 BM25가 순위의 약 72%를 결정했다(명목 30%). 벡터 단독보다 카테고리 오답이 늘어난 이유다(44 → 69건).
- **원인 2. 검색 문서에 구매자가 찾는 정보가 없거나 틀렸다** (A-21):
  - 가격·연식·수량·상태가 BM25 텍스트에도 임베딩 텍스트에도 없었다.
  - 임베딩 텍스트는 `cycles`·`predictedRange`를 읽었지만 실제 필드는 `cycleCount`·`estimatedMileageKm`이다.
  - 카테고리 단위 고정 키워드가 사실과 다른 정보를 넣었다(SiC 인버터에 IGBT, 유도 모터에 PMSM, 강철 도어에 알루미늄).
  - 운영에서는 BM25가 METADATA만 읽어, SPEC 항목(184개)의 사양이 보이지 않았다.
  - 운영 부품 중 차종이 나오는 90개의 89%(80개)가 영문 표기만 쓴다(`IONIQ 5`). 한글 질의(`아이오닉5`, 실제 검색 기록의 `기아EV`)는 BM25에서 맞을 수 없다.
- **원인 3. 텍스트 검색으로는 부등호 조건을 풀 수 없다**: 수치·거래 조건 위반(33%)은 문서와 결합을 고친 뒤에도 거의 줄지 않았다(수치 사양 72 → 70건). 질의에서 조건을 뽑아 필터로 쓰는 질의 이해가 필요하다. 다음 단계로 둔다.
- **실험** (구성 96개, `reports/2026-11-05-v2-experiments-root-cause.md`). 문서 정의 효과를 검색기별로 분리했다(test nDCG@10).

| Haiku 5.5, Sonnet 5.5 | **NOT_AVAILABLE** | AUTHORIZED | AVAILABLE | AVAILABLE |

- **약정 수락 후 (사용자 승인, 2026-11-05)**

### A-22 차종·제조사 표기 변형 사전 · 2026-11-05 · 측정 + 판단

- 문서에 나온 표기를 찾아 같은 묶음의 다른 표기를 문서에 덧붙인다(문서 확장). 질의는 바꾸지 않으므로 검색 시점 비용이 없다.
- 부분 문자열이 아니라 단어 1~3개를 이어 붙여 비교한다. "리프트"는 "리프"가 아니다. 뜻이 여럿인 짧은 표기(볼트 = 체결 부품)는 단독으로 넣지 않는다.
- **측정값은 상한이다**: 평가 코퍼스는 문서마다 차종 표기를 바꿔 쓰도록 만들었고(`vehicles.py`), 사전이 그 변형을 대부분 덮는다. 사전의 기여는 BM25 단독 +0.089, 현재 구조 +0.044, 독립 결합 +0.028이다.
- 실제 효과의 독립 근거는 운영 데이터다. 차종이 나오는 부품의 89%가 영문 표기만 쓴다.
- 재검토 조건: 운영 검색 기록이 쌓이면 사전에 없는 표기(결과 0건 질의)를 모아 사전을 보강한다. 사전 변경도 평가 게이트를 통과해야 한다.

### A-23 BM25 색인은 Lambda 메모리에 두고 5분마다 다시 읽는다 · 2026-11-05 · 공식 제약 + 판단

- 재검토 조건: 부품 5,000개 이상이거나 IndexLoadMs p95가 300ms를 넘으면 S3에 직렬화한 색인이나 외부 검색 엔진으로 옮긴다.
  - 관리형 검색 엔진(OpenSearch Serverless)은 이 규모에서 고정 비용이 검색 품질 이득보다 크다고 보고 도입하지 않았다.

### A-26 더미 부품 데이터의 모순 정리 · 2026-11-06 · 공식 자료 + 판단

- 운영 데이터는 전부 합성·더미라서 값을 고쳐도 된다(사용자 확인). `backend/scripts/fix-dummy-data-consistency.ts`(dry run 기본)로 44개를 고쳤다.
  - 상태 등급 16개
  - 배터리 상태 보충 12개
  - 출시 전 연식 9개
  - 카테고리 10개
- **상태 등급**(`consistentBatteryCondition`, 판단):
  - new: SOH 98% 이상, 충방전 10회 이하
  - like-new: SOH 95% 이상, 충방전 100회 이하
  - excellent: SOH 90% 이상
  - 맞지 않으면 SOH 구간으로 다시 매긴다: 85% 이상 good, 70% 이상 fair, 그 미만 poor.

  - SOH: 설명에 적힌 값(3개)을 쓰고, 없으면 연식으로 추정했다. 추정식은 SOH = 100 − 1.8 × 경과 연수다(Geotab 2024, EV 약 5,000대 분석의 연평균 열화율 1.8%). 추정값에는 `estimated: true`를 남겼다.
  - 양극재·셀 제조사: E-GMP 공개 사양(SK온 NCM)을 썼다.
- **출시 전 연식**: 아이오닉5·EV6(2021년 출시)만 출시 연도로 올렸다. 다른 차종의 연식 검증은 출시 연도표가 없어 하지 않았다.
- **polymer 카테고리 10개**: 재질 분류가 부품 종류 자리에 들어가 구매자 필터에서 보이지 않았다. 부품 이름으로 body-panel·interior·electronics·other로 옮겼다. 재질은 SPEC에 그대로 남는다.
- 재검토 조건: 실제 판매자 등록이 생기면 같은 규칙을 등록 시 검증으로 옮긴다.

### A-27 질의 조건 감점 재정렬과 비교용 속성 저장 · 2026-11-06 · 측정

- 질의에서 카테고리·수치·상태 조건을 뽑아(`query-understanding.ts`) 부품 속성(`search-attributes.ts`)과 비교한다. 위반 1개마다 점수에 0.2를 곱한다(감점 0.8, E-25 dev 선택, E-26 v3 확인).
  - 필터가 아니라 감점이라 결과가 비지 않는다. 확인할 수 없는 조건은 감점하지 않는다.

### A-28 결과 설명 프롬프트가 적합하다는 결론을 전제하지 않게 한다 · 2026-11-06 · 운영 관측

### A-29 운영 순위 로직을 CI 게이트에 넣는다 (게이트용 임베딩 커밋) · 2026-11-06 · 측정 + 판단

- CI 게이트는 비용 때문에 BM25 단독만 검사했다. 그런데 이번 변경에서 BM25 단독은 일부 그룹이 떨어졌고, 운영 파이프라인은 모든 그룹이 올랐다.
  - BM25 단독 하락 예: v1 mixed nDCG 0.671 → 0.612, v1 recall@10 0.884 → 0.862, v2 F-conversion 0.675 → 0.631
  - 운영 파이프라인: v2 0.776 → 0.876, v1 0.882 → 0.935
- 즉 게이트가 운영과 다른 대상을 재고 있었다. BM25 단독 기준값은 의도한 변경으로 갱신하고, 운영 순위 게이트(prod-hybrid, v2·v3)를 추가한다.
- 질의 벡터와 현재 문서 벡터만 gzip으로 묶어 `datasets/<v>/gate-embeddings.json.gz`로 커밋한다. 크기는 v2 1.8MB, v3 1.3MB다. CI에 AWS 자격 증명이 필요 없다.
- 묶음에는 문서 텍스트 해시(`docTextSha256`)가 들어 있다. 문서 정의가 바뀌면 게이트가 "임베딩을 다시 만들라"며 실패한다.
- 재검토 조건: 저장소 크기가 문제가 되면(묶음 갱신이 잦아지면) Git LFS나 CI 캐시 아티팩트로 옮긴다.

### A-30 결과 설명을 검색 응답과 분리한다 · 2026-11-06 · 측정

- 운영 v1.7.0에서 설명이 응답 시간의 83%였다(평균 1,538ms / 1,850ms, EMF). 검색 순위 계산은 평균 6ms다.
- 검색 요청에 `explain=false`를 주면 LLM 없이 바로 응답한다. `reason`에는 규칙으로 확인한 조건 요약을 넣는다(`summarizeCheck`, 예: "조건 불일치: 용량 17.6kWh (일치: 카테고리)"). 그리고 `reasonSource: 'rules'`로 표시한다.
- 설명은 `POST /api/search/explain {query, partIds}`로 따로 받는다(같은 Lambda, 최대 20개, 7일 캐시). 폴백 설명은 캐시하지 않는다.
- 프론트엔드는 결과를 먼저 보여 주고, 화면에 보이는 결과의 설명만 요청해 채운다.
- 결과 카드의 "87% 일치" 배지는 목록 안 상대 점수(score)에 100을 곱한 값이었다. 일치도가 아니고 1위는 거의 항상 100%다. 그래서 규칙으로 확인한 "조건 n/m 일치"로 바꿨다.
- `explain` 기본값은 true로 두어 기존 클라이언트는 그대로 동작한다. 캐시 키에 explain을 넣었다.

### A-31 프론트엔드 커버리지 임계값은 적용된 적이 없었다 · 2026-11-06 · 측정

- `vitest.config.ts`는 `thresholds: { global: {...70} }`로 적혀 있었다. `global`은 Jest 문법이라 Vitest 4가 무시했다. 문서(CLAUDE.md)의 "커버리지 70%"는 프론트엔드에서 한 번도 검사되지 않았다.
- 올바른 문법으로 고치면 현재 커버리지(구문 27.9%, 분기 18.4%, 함수 18%, 줄 29.4%)에서 바로 실패한다.
- 결정: 문법을 고치고 **현재값을 하한으로 고정**한다(구문 27, 분기 18, 함수 18, 줄 29). 검사가 없던 상태보다 엄격하다. 커버리지를 올리면 하한도 함께 올린다.
- 백엔드(Jest)의 70%는 실제로 적용되고 있다(현재 약 93%).
